# ВышКат — Домашнее задание №1 (КПО)

## Запуск

* Запуск приложения: `./gradlew run`
* Запуск тестов: `./gradlew test`

## Архитектура и SOLID

* **SRP:** Каждая сущность решает одну задачу: `ServiceCenter` проверяет дефекты, `DefaultBeginnerPolicy` фильтрует
  технику по дружелюбности, `InMemoryFleetRepository` хранит состояние, `FleetService` управляет приёмкой и отчётами.
* **OCP:** Новые виды транспорта (`IVehicle`, `IEnergyConsumer`) и вещей (`IInventoryItem`) добавляются созданием новых
  классов без правки логики сервисов.
* **LSP:** Любая реализация `IVehicle` (`Kickscooter`, `Bicycle`, `ElectricBike`) взаимозаменяема в репозитории и
  сервисе без нарушения контрактов.
* **ISP:** Абстракции разделены: `IInventoryItem` (инвентарный номер), `IEnergyConsumer` (энергия), `IVehicle` (прокат).
  Велосипед не реализует `IEnergyConsumer`, а шлем — `IVehicle`.
* **DIP:** `FleetService` зависит от интерфейсов `IFleetRepository`, `ITechnicalInspectionService`, `IBeginnerPolicy`,
  внедряемых через `DiContainer`.

## Ответы на вопросы

1. **Какой принцип SOLID применён наиболее явно и где:**  
   **ISP** в интерфейсах `IInventoryItem`, `IEnergyConsumer`, `IVehicle`. Сущности комбинируют только нужные контракты:
   механический `Bicycle` не зависит от `dailyEnergyConsumptionKWh`, а `ChargingStation` не содержит полей проката
2. **Какой принцип сознательно ограничен / «почти нарушен» и почему это приемлемо:**  
   **OCP** в методе `ServiceCenter.inspect`: сейчас проверка опирается на флаг `vehicle.hasMechanicalDefect`. Для
   расширения логики осмотра конкретных видов транспорта лучше было бы ввести цепочку флагов/валидаторов, но для
   нынешнего тз это перебор
3. **Что сломается / не сломается при расширении:**
    * **Новый транспорт:** ничего не сломается, достаточно объявить класс, реализующий `IVehicle`
    * **Сотрудники:** не ставятся на баланс, поэтому будет необходимо создавать для них отдельную сущность
    * **Склад запчастей:** запчасти могут реализовывать `IInventoryItem` и ставиться на баланс через `registerItem`
4. **Какой тест фиксирует решение техосмотра / правило «для новичков» и как подменяется зависимость:**
    * Техосмотр и правило новичков: тесты `inspection approves sound and rejects defective` и
      `beginner policy checks threshold`
    * Подмена зависимости через DI: тест `di container resolves singletons transients and stub override`, где
      `ITechnicalInspectionService` подменяется анонимным объектом-заглушкой при вызове `configureContainer`
5. **Роль ИИ:**  
   ИИ использовался для приведения консольного вывода в `main` и текста в `readme` к более красивому формату, а также
   написания некоторых из тестов
